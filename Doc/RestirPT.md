# ReSTIR PT

## Introduction

Reservoir-based SpatioTemporal Importance Resampling for Path Tracing (ReSTIR PT) is a resampling algorithm for path tracers that dramatically increases the effective sample count per pixel. ReSTIR PT enables more intelligent path reuse between pixels, allowing high quality light paths to quickly propagate across the screen and accumulate over time. Unlike ReSTIR GI, ReSTIR PT also works well for specular surfaces with low roughness as its reuse applies a more general shift mapping method.

ReSTIR PT is an embodiment of [Generalized Resampled Importance Sampling by Lin et al.](https://d1qx31qr3h6wln.cloudfront.net/publications/sig22_GRIS.pdf)

The runtime functions and structures for ReSTIR PT are defined in the header files under [`PT/`](../Libraries/Rtxdi/Include/Rtxdi/PT/) and documented in full in the [ReSTIR PT Shader API reference](ShaderAPI-RestirPT.md) — the authoritative reference for the symbols named on this page. The application-side bridge functions are documented in [RtxdiApplicationBridge.md](RtxdiApplicationBridge.md). The [Full Sample](../Samples/FullSample/Shaders/LightingPasses/PT/) provides a complete, working integration that can be used as a reference implementation.

## Algorithm Integration Overview

ReSTIR PT starts by acquiring initial samples from a path tracer. The RTXDI runtime requires that an `RAB_PathTrace` function be implemented accordingly. The implementation of the path tracer is up to the developer, but it must call all of the required functions of the `RTXDI_PathTracerContext` at the proper times. These functions primarily relate to recording the surface of each bounce, as well as whether light is being sampled for the path via emission from the hit surface, next event estimation (NEE), or the environment map on miss. At the end of the path tracing loop, the `RTXDI_PathTracerContext` has the information needed to create an `RTXDI_PTReservoir` data structure, which stores the information required for resampling paths between pixels. Note that the reservoir does **not** store the accumulated radiance from all light sources along the path, but instead selects a single path from all of the potential ones it receives.

The temporal resampling pass uses motion vector data to reproject a pixel's surface back into the previous frame. If the previous frame's surface is sufficiently similar to the current frame's surface, ReSTIR PT tries to use the previous frame's reservoir to generate a path in the present frame that is similar to the one used to generate the previous frame's reservoir. This process of transforming a path taken from one domain into a similar path taken from a similar domain is known as shift mapping. (There are several methods of shift mapping, and RTXDI uses its own hybrid shift, more details of which are explained in a dedicated section below.) If the shift mapping is successful, then the current pixel's reservoir is updated to use the shifted path with probability proportional to its quality. 

The spatial resampling pass is similar to the temporal resampling pass, but it resamples nearby pixels within the same frame, rather than a single reprojected pixel in the previous frame.

Nearly all of the integration work required for ReSTIR PT resides in implementing `RAB_PathTrace` and calling the `RTXDI_PathTracerContext` properly. The runtime entry points these interact with — `GenerateInitialSamples`, `RTXDI_PTTemporalResampling`, `RTXDI_PTSpatialResampling`, and the reservoir helpers — are documented in the [Shader API reference](ShaderAPI-RestirPT.md), and the `RAB_*` bridge functions in [RtxdiApplicationBridge.md](RtxdiApplicationBridge.md). The Full Sample's implementation of `RAB_PathTrace` is a useful reference to see them wired together end to end. The `RTXDI_ComputeHybridShift` function employed by temporal and spatial resampling passes reuses `RAB_PathTrace` for generating most of the new path. The shift mapping logic inherently requires that some of the path tracing functionality be handled by `RTXDI_ComputeHybridShift` after `RAB_PathTrace` has finished. As a result, developers must implement several additional `RAB_*` functions (documented in [RtxdiApplicationBridge.md](RtxdiApplicationBridge.md)) to bridge this gap. The good news is that because these functions need to replicate logic that is already implemented by the path tracer, there is little additional work that needs to be done. In fact, it is recommended developers use these callbacks inside the path tracer to ensure consistency between initial sampling and hybrid shift.

The reservoir contains all the information required to shade the pixel's indirect lighting contribution. The product of the `weightSum` and `targetFunction` fields in the `RTXDI_PTReservoir` produces the final radiance value, which can then be apportioned to the diffuse and specular components by the application's shading code as needed. If the reservoir's `rcVertexLength` field is greater than 2, the incoming light direction needs to be regenerated to match the one used in `RAB_PathTrace` (see `RTXDI_GetRngForShading` in the [Shader API reference](ShaderAPI-RestirPT.md#rtxdi_getrngforshading)). The full `RTXDI_PTReservoir` layout is documented in the [Shader API reference](ShaderAPI-RestirPT.md#rtxdi_ptreservoir); see [`PT/FinalShading.hlsl`](../Samples/FullSample/Shaders/LightingPasses/PT/FinalShading.hlsl) for a worked example.

## Hybrid Shift

A path from one pixel cannot simply be donated to another pixel. The neighboring pixel's path must be sufficiently similar to one taken from the target reservoir, and even then the exact path isn't shared, but is instead recreated as though it had come from the target pixel. This process of intelligently translating path information between pixels is called shift mapping, and ReSTIR PT makes use of a particular method of shift mapping called hybrid shift.

The name *hybrid* reflects a combination of two shift strategies. A pure **reconnection shift** — as used by ReSTIR GI, which reuses a path by reconnecting the primary surface directly to the secondary vertex — is cheap but fails if any of these two vertices have low roughness specular material. Retracing the whole path with **random replay** stays valid on specular transport but costs more and adds noise due to gradual deviation of path shapes. Hybrid shift combines the two: it replays only the specular/glossy prefix of a path and reconnects once a pair of vertices is rough and far enough apart, keeping reuse well-behaved across low-roughness specular vertices and multi-bounce transport of mixed vertex types.

### Recording Hybrid Shift Data During Initial Sampling

Some data for hybrid shift is precomputed during initial sampling. At each bounce in the path, the `RTXDI_PathTracerContext` tests whether a consecutive pair of vertices is *reconnectible* — intuitively, whether the scattering at both is spread out enough (rough, non-specular) and the two are separated enough that a shifted path could later connect with minimal loss of throughput. When a pair qualifies, the context records the second vertex as the reconnection vertex, or `RcVertex`. The precise test is selected by `RTXDI_PTReconnectionParameters::reconnectionMode` — either fixed roughness and distance thresholds or a footprint-based criterion (see [Reconnection Criteria and the Footprint Threshold](#reconnection-criteria-and-the-footprint-threshold) below). The utility of this reconnection vertex becomes clear in the discussion of random replay below.

Independently of this process for determining the reconnection vertex, the `RTXDI_PathTracerContext` also analyzes each potential path to the light as it is sampled via emissive hit surface evaluation, NEE, or the environment map when the ray misses. The context stochastically chooses the light path in proportion to its contribution, such that the brightest paths have the highest chances of being selected.

At the end of the initial path tracing loop, the context is left with the following key pieces of information:

- A final bounce depth from the primary surface to the winning light source
- A reconnection vertex depth, if one was found
- The random number state used to generate the path via BRDF sampling
- Additional information related to reconnection (explained below) and key probability values.

### Shifting From One Path To Another

The `RTXDI_ComputeHybridShift` function, whether called from the temporal resampling pass or the spatial resampling pass, uses reservoir information to shift a temporal or spatial neighbor reservoir's path into the target reservoir's domain (or vice versa when computing the contribution MIS weight in `BiasCorrection`).

- First, the two neighboring surfaces are compared for material and geometric similarity. If they are too dissimilar, the hybrid shift fails immediately. For example, the best light path for a pixel on a glossy fork is unlikely to be a good path for a pixel on the diffuse napkin beneath it.
- If the neighboring surfaces are similar, the `RAB_PathTrace` function is invoked in a process called **random replay**. Random replay regenerates a path starting from the target surface using the neighbor reservoir's cached random number state that was used to generate its own path. The spatial and temporal coherence of the scene generally means that this replayed path, though offset in time and space, is highly likely to produce a path from the target surface that provides a very similar amount of light to the one generated for the neighbor surface.
- However, the path is not always replayed in its entirety. If the neighbor path has a reconnection vertex along it at bounce N, then the random replay path can divert to it from bounce N-1 and avoid tracing the rest of the path. The reason the reconnection vertex and the one before it must be sufficiently rough is to ensure minimal loss in throughput as a result of diverting the path. If one surface were instead glossy, for example, then the likelihood that it would reflect the same light towards the shifted N-1 vertex is much lower.
- When the path reconnects to an NEE-sampled light, the last bounce of the path tracer is handled by `RTXDI_ComputeHybridShift` itself (forced reconnection), rather than inside `RAB_PathTrace`. It samples this light through the same `RAB_*` functions as ReSTIR DI, plus one additional bridge callback — `RAB_GetMISWeightForNEE` — to MIS-weight the reconnected light against BRDF sampling. (The emissive-hit and environment-miss MIS cases are handled by the path tracer inside `RAB_PathTrace`.)

### `RTXDI_PathTracerContext` during random replay

During the random replay process, the `RTXDI_PathTracerContext` no longer considers alternate light paths through the scene. In fact, it signals to `RAB_PathTrace` that it should not sample any light sources except potentially the one ultimately chosen in the original path. Instead, it analyzes whether the replayed path meets the various algorithmic requirements of ReSTIR PT. One such requirement is that the reconnection vertex must arise at the same point in the path as in the neighbor's path, or not at all if the neighbor's path does not have one. Thus, if bounces 3 and 4 in the neighbor's path are rough and distant, but the path replayed from the target surface encounters a glossy surface at bounce 3, then the shift is invalid and resampling halts.

### Reconnection Criteria and the Footprint Threshold

A path's *reconnection vertex* is chosen when the path is first generated; which vertices qualify is controlled by `RTXDI_PTReconnectionParameters::reconnectionMode`:

- **`FixedThreshold`** — the classic criterion: a vertex is reconnectible when both it and the preceding vertex are rough enough (surface roughness above `roughnessThreshold`) *and* far enough apart (reconnection distance above `distanceThreshold`).
- **`Footprint`** — the footprint-based criteria from [*ReSTIR PT Enhanced: Algorithmic Advances for Faster and More Robust ReSTIR Path Tracing*](https://dl.acm.org/doi/10.1145/3804494). Each scattered ray has a *footprint* that grows with reconnection distance and with lower BSDF sampling density (i.e. rougher scattering; delta/mirror bounces have zero footprint). Because the footprint characterizes how much the sample density changes when a path is reconnected, bounding it constrains the resulting deviation in path contribution after the shift — a more robust test than fixed roughness/distance cutoffs on glossy transport. Concretely, the ray's footprint is compared against a threshold derived from the primary ray's footprint scaled by `minConnectionFootprint`, and an inverse-footprint threshold additionally bounds the BSDF change at the glossy reconnection vertex (sharing the same threshold). The preceding vertex is also held to a PDF threshold (`minPdfRoughness`) that acts as a more adaptive roughness threshold, covering corner cases where the footprint test alone is inaccurate. All of these thresholds can be stochastically jittered per sample (`minConnectionFootprintSigma`, `minPdfRoughnessSigma`) to soften the decision boundary and avoid structured artifacts.

## Compatibility-Guided Spatial Neighbor Selection

By default, spatial reuse draws neighbor pixels uniformly from a disk and rejects those failing a binary G-buffer normal/depth test. RTXDI also implements the *compatibility-guided neighbor selection* of [Junkins et al., *Compatibility-Guided Neighbor Selection for ReSTIR*](https://doi.org/10.1145/3820024), enabled via `RTXDI_PTSpatialResamplingParameters::enableSpatialHeuristicMode`. It replaces the binary test with a continuous geometric compatibility score — the product of a normal term `max(n·nᵢ, 0)^β` and a primary-hit-position term `exp(−‖x₁ − yᵢ‖ / s)`, with `s = √(Ω·d²/π)` (using `Ω = 0.05`, `β = 8`, and primary-hit distance `d`) — and uses weighted reservoir sampling over `K` candidate pixels drawn from the search disk to select the best neighbors, terminating early once enough high-scoring candidates (score > 0.5) are found. Reusing the most compatible available neighbors, rather than giving up when no strictly-above-threshold neighbor exists, reduces both image error and temporal correlation, especially around complex geometry. The selection runs as a separate pass (`RTXDI_PTSpatialNeighborSelection`) that writes the chosen neighbors to `RTXDI_SPATIAL_NEIGHBOR_SELECTION_BUFFER` for the spatial resampling pass to consume; see the [Shader API](ShaderAPI-RestirPT.md#neighbor-selection-and-duplication-map).

## Duplication-Based History Reduction

Temporal reuse raises a reservoir's confidence (its effective sample count `M`, capped by `maxHistoryLength`) over successive frames. But where the same sample is duplicated across many pixels, that accumulated confidence turns into strong spatiotemporal correlation, which slows adaptation and lets fireflies persist. Following [*ReSTIR PT Enhanced*](https://dl.acm.org/doi/10.1145/3804494), RTXDI lowers the temporal confidence cap where duplication is high. A duplication map (`RTXDI_PTComputeDuplicationMap`) counts, per pixel, how many neighbors in a 17×17 window carry the same sample ID; during temporal resampling the per-pixel history cap is interpolated from `maxHistoryLength` toward 1 as that normalized duplication ("impoverishment") rises. `historyReductionStrength` sets the exponent of the power curve applied to the impoverishment ratio, controlling how aggressively the cap falls: higher values pull the cap toward 1 even under modest duplication, while lower values only reduce it where duplication is heavy. It is enabled via `duplicationBasedHistoryReduction` (set on both the temporal and spatial parameters) and trades a small amount of variance for substantially reduced temporal correlation, which is especially valuable ahead of a denoiser. The per-pixel sample IDs the map is built from are written by `RTXDI_PTStoreDuplicationInputs` from the last resampling pass when `RTXDI_PTNeedsDuplicationInputs` is true.

## Decorrelation for DLSS Ray Reconstruction

DLSS Ray Reconstruction (DLSS-RR) expects temporally uncorrelated input noise, whereas ReSTIR's temporal reuse deliberately correlates samples across frames — enough that DLSS-RR can mistake the correlation for signal and produce artifacts. To stay compatible, final shading applies a **stochastic decorrelation**, framed as a 1-sample MIS between the resampled and initial sample with a constant MIS weight: with probability `decorrelationFactor` (0–1) a pixel discards its resampled reservoir and instead shades the preserved, unresampled *initial-sampling* reservoir (temporally independent, kept in a dedicated buffer slot). The swap is a per-pixel Bernoulli trial — final shading forms the effective probability `scaledDecorrelationFactor`, draws one uniform random number, and replaces the resampled reservoir when the draw falls below it. Configured through `RTXDI_PTDecorrelationParameters`, a constant `decorrelationFactor` would need a globally high value to clear artifacts in strongly-correlated regions; `decorrelationMode` therefore scales the base factor into `scaledDecorrelationFactor` with a per-pixel correlation measure, so highly-correlated pixels ramp up automatically while the base stays low:

- **Decorrelation probability** — `Uniform` uses `decorrelationFactor` directly. `Stagnancy` scales it by a *stagnancy* signal — how long a pixel has kept the same sample without a fresh one being drawn (from the reservoir `age`) — shaped by `decorrelationStagnancyExponent`, so stale pixels decorrelate more and freshly-refreshed ones are left intact. Raw per-pixel stagnancy comes from the very sample being shaded, so using it directly biases the estimate (visible darkening); `RTXDI_PTComputeSmoothedDuplicationMap` first spatiotemporally filters it (a 5×5 à-trous average plus an EMA, `decorrelationEmaFactor`), turning it into a statistic that is largely independent of the current sample and removing most of that bias.
- **Firefly replacement** — with `fireflyReplacementFilterEnable`, a boiling filter (`fireflyReplacementFilterStrength`) at the end of spatial resampling flags outlier (firefly) pixels and force-decorrelates them (probability 1), so a persistent firefly is replaced by the fresh initial sample instead of being smeared across frames by DLSS-RR's accumulation.
- **Bias reduction** — firefly replacement on its own brightens the image: ReSTIR's firefly is often correlated with the current frame's initial sample, so the swap tends to trade one firefly for an even higher-energy one (initial samples have higher variance). When the firefly is new (`age` 0), `fireflyReplacementBiasReduction` clamps the replacement's `weightSum` (its UCW) to at most `fireflyReplacementMultiplyBound ×` the resampled weight, which tames that bias.

The per-pixel inputs for this feature are written by `RTXDI_PTStoreDuplicationInputs` during the last resampling pass, when `RTXDI_PTNeedsDuplicationInputs` is true. Final shading applies the swap through `RTXDI_PTApplyDecorrelation` (see [`PT/Decorrelation.hlsli`](../Libraries/Rtxdi/Include/Rtxdi/PT/Decorrelation.hlsli) and the [Shader API](ShaderAPI-RestirPT.md#decorrelation)).

## `RAB_PathTracerUserData`

The `RAB_PathTracerUserData` struct provides a way for the application-defined `RAB_PathTrace` function to send information back out from the RTXDI runtime functions to their callers. This struct is used in the sample to collect PSR information for the denoiser (explained below). The struct also must implement the trivial `RAB_PathTracerUserDataSetPathType` function, which the runtime functions use to tell the path tracer which part of the resampling algorithm it's being called from. The sample's PSR implementation uses this field to disable PSR updates during inverse shift mappings, which are only done to check for correctness.

## Denoiser Integration

Path tracers are stochastic algorithms that produce noisy outputs. One approach to removing noise is to accumulate many samples until the final image converges. However, even with ReSTIR PT, this process is too slow for real time applications. Instead, path tracing output is sent to a dedicated denoiser algorithm, which, as its name suggests, smooths out the signal. Denoisers require many pieces of information per pixel, such as the surface's location, normal, and material properties. This information is fed to denoisers on a per-pixel basis via textures called "guide buffers."

For non-mirror primary surfaces, the GBuffer fill pass generates most of the denoiser guide buffers anyway, and lighting passes generate diffuse and specular `hitT` values.

However, denoising of mirror surfaces can be optimized by Primary Surface Replacement (PSR) in denoisers like NRD. The interaction between PSR and ReSTIR PT's resampling logic is fairly complicated, since resampling changes the correct values for the guide buffers. Likewise, features like Russian roulette that stochastically terminate paths early need to be disabled during mirror bounces to avoid generating improperly noisy guide buffers.
